Three copilot-delegation facts (2026-07-17):

0. **Budgets HIGH — never choke workers (Rutvik directive 2026-07-17, ULTRAAUDIT session: "dont put damn budgets, let the agents free!"). SHARPENED 2026-07-24 (3rd recurrence, Rutvik: "stop giving less damn credits, give 2x credits of what is required"): the formula is ESTIMATE × 2, floor ~250-400 for research/build.** `--max-credits` stays only as a runaway backstop. Evidence: a 130cr cap caused one outright cap-death (gpt at 141/130) AND silent self-rationing (opus truncated 3 large plan reads) — and on 2026-07-24 a 50cr chief died with ZERO deliverables and 40cr gpt reviews died mid-read TWICE (dtemp 7-death cluster) despite this fact already prescribing 250-400. A choked worker = failed run + re-dispatch = MORE waste than a generous cap. **How to apply: estimate the job's credits (reads + writes + model tier), dispatch at 2× that, never below the floor.**

1. **`--max-credits` floor is 30.** `copilot-worker.sh ... --max-credits <N>` with N<30 hard-fails: `option '--max-ai-credits' argument 'N' is invalid ... Use at least 30 AI credits.` Cost 2 dead probe dispatches (I sent 4). Always pass ≥30; use ~40 for normal build/rca, more for big fan-out.

2. **`verify-run.mjs` emits false-FABRICATED on operations that don't change file CONTENT.** It keys on manifest sha256; a `git rm --cached` (untrack) leaves content byte-identical → it reports `FABRICATED: sha256 unchanged`, and a text-scrub that removes a string it parsed as a "created file" claim → `UNPROVABLE: file not found`. Both are tool blind spots, NOT worker fraud. Per the three-way acceptance law, route these to JUDGMENT: re-verify the actual requirement directly on disk (`git status --porcelain`, `git grep` zero-hit, `tsc`), and override the verdict with the disk facts in the receipt. Do NOT auto-bounce an honest worker on a FABRICATED that only means "content hash unchanged" when content-change was never the requirement.

Related: [[never-conclude-from-redacted-or-name-only-match]] (same session's bigger lesson — always read the VALUE, not the tool's summary of it).

- **--max-credits for opus multi-file builds**: 120 exhausted mid-build (data+helpers landed, TCs not) -> needed a continuation. Use >=180 for opus builds authoring multiple TCs + parity docs + gates. A graceful credit-cap stop shows `exit_reason=success` + `ok=true` but a PARTIAL report — verify the JOB (files on disk) not just the exit code.

3. **REFUTED — there is NO copilot sandbox block on `playwright-cli`. It works.** Capture probe 2026-07-22 run INSIDE a copilot worker: `playwright-cli open https://example.com` -> "Browser `default` opened with pid 3304", real page title, snapshot written, **EXIT=0**; repeated with `--browser chromium` -> pid 28212, **EXIT=0**. Version 0.1.8 at `%APPDATA%\npm\playwright-cli`. `npx playwright test --list` (764 tests) and `npx playwright screenshot` also EXIT=0 there. => **LIVE playwright-cli walks CAN be delegated to copilot workers.** The `npx playwright test` throwaway-spec route still works and is a fine alternative, but it is OPTIONAL, not a required workaround.

   The 2026-07-21 walk-A "Permission denied and could not request permission from user" + ENV-BLOCK verdict was therefore a **FALSE BLOCKER**. Its cause remains unknown — raw stderr was never captured (`err.txt` empty). Unverified candidate if it ever recurs: a concurrent playwright-cli session was open from the main loop at that moment (possible session/port conflict). Do NOT record that as the cause without a capture.

   **Meta-lesson (I got this wrong TWICE in a row):** first I recorded the agent's "can't do X" verdict as a capability fact; then I "corrected" it to "symptom, cause unknown" — still wrong. The real answer was "the tool works fine." Any ENV-BLOCK / not-automatable / permission-denied verdict from ANY agent must be REPRODUCED with a raw stdout+stderr+exit-code capture before it is believed, acted on, or written to memory. This is LR-061 §B (verify-before-blocked) applied to the delegation layer ([[copilot-output-untrusted]] + [[real-verification]] + [[stop-guessing]]).

4. **`--model <id>` can be IGNORED — the custom-agent model pin wins.** Dispatched `--model claude-opus-4.6`; the run's `process-*.log` said `Using model "claude-sonnet-4.6" from custom agent "council-worker"`. Always confirm the ACTUAL model in the ledger row / process log — never assume the flag took. (2026-07-24 update: the wrapper now closes this trap by materializing `--model` into a variant agent whose pin IS the requested model — but the confirm-the-log rule stands, and see #7 for the sonnet-4.6 resolver bug that survives even a correct pin.)

5. **Self-miss: under-budgeting still bites.** I dispatched a full read+reason+write gate-analysis at `--max-credits 50` and a read+write+run harvest at `60` — BOTH walled before writing their deliverable (fact 0 already prescribes 250-400). A run-only re-dispatch (pre-written spec, 55cr) rescued the harvest only because the job was tiny. The fix is fact 0, not "split to run-only": budget HIGH whenever a job must read+reason+write.

7. **SONNET-4.6 agent-mode dispatches fall to haiku — Copilot CLI 1.0.74 custom-agent resolver bug (RCA'd 2026-07-24, cross-provider probes + CEO-verified decisive reads).** NOT "the CLI swaps models" and NOT an agent pinned to haiku: `council-worker.agent.md` pins `claude-sonnet-4.6`, and the wrapper correctly materializes `council-worker--<model>` variant agents with the requested model as the pin (body copied verbatim, so `name:` stays `council-worker` — which is why every log says `from custom agent "council-worker"`). The real defect: CLI 1.0.74's CUSTOM-AGENT model resolution misresolves a `claude-sonnet-4.6` pin to `claude-haiku-4.5` (Anthropic lightweight fallback), while agent pins for opus-4.6 / sonnet-4.5 / gpt-5.5 resolve correctly and direct `--model claude-sonnet-4.6` (no `--agent`) serves real sonnet — all proven by 3 controlled pin-probes + flag contrast (raw-swap-b2). The wrapper then passes `--effort` computed from the REQUESTED sonnet; haiku has no reasoning_effort enum; exit 1. Explains "worked for ages then broke": agent-pinned sonnet-4.6 ran fine pre-2026-07-22 (ledger pwch-2/3) — the resolver bug arrived with a CLI update. Recipe: sonnet-4.6 agent-mode = UNUSABLE until a CLI update fixes the resolver (re-probe after upgrades); use opus/gpt/haiku agent-mode or `--model claude-sonnet-4.6` without `--agent`; always confirm the process log's `Using model` line before trusting the ledger's model field. Resolver source line uncaptured (bundle read denied in worker sandbox) — behavior-level proof only.

8. **The CAPI `/models` catalog is NOT the CLI's `--model` allowlist — catalog `policy.state: enabled` does NOT mean dispatchable (2026-07-26).** The debug log's `fetched models from CAPI /models` line lists **28** models including `gemini-2.5-pro` (vendor Google, `policy.state: enabled`, `model_picker_enabled: true`, `preview: false`, billing entitlement BROADER than gpt-5.5's). It is still **rejected** by `copilot -p ... --model gemini-2.5-pro` → `Error: Model "gemini-2.5-pro" from --model flag is not available.` — byte-identical to the message for a fabricated model id. Proven with a **4-way control matrix**: positive controls `claude-opus-4.6` (16.3cr, 12s) and `gpt-5.5` (11cr, 17s) both RAN; negative controls `gemini-2.5-pro` and `ZZZ-fake-model-does-not-exist` both rejected. **So `~/.claude/delegation/candidates.txt`'s "CONFIRMED UNAVAILABLE" for gemini/grok/o3/o4-mini is CORRECT — do not "correct" it from catalog data.** I doubted it on catalog evidence and the live probe proved the original finding right. Consequence: **two vendors only (Anthropic + OpenAI)** for cross-vendor review — there is no third-vendor seat available, so "no provider grades its own homework" tops out at 2. Also note `gemini-2.5-pro` has `reasoning_effort: null` (no tiers), so any probe passing `--effort` would fail for that reason alone and be misread as unavailable — see #6. Related: [[feedback-gate-trip-probes-need-valid-payloads]] (a probe without a positive control proves nothing).

9. **The model-provenance guard kills a SUCCESSFUL opus run at the recording step (2026-07-27, ×2 in one session).** `copilot-worker: FATAL — debug log contains MULTIPLE DISTINCT models: claude-haiku-4.5 claude-opus-4.6 — refusing to record.` Process exits 1 (or 124's sibling path), no ledger row is written — but **the worker's actual repo changes are already on disk and complete**. Both hits were `--agent council-planner` (opus-4.6); zero hits on `--agent council-worker` (sonnet-4.6) across ~15 dispatches the same session. Cause is that an opus worker session invokes haiku internally for something, and the guard cannot distinguish that from model substitution — it is a false positive of an otherwise correct anti-fraud check.

   **SCOPE CORRECTION (2026-07-30, q123 tri-plan session): the trigger is the OPUS MODEL, not the `council-planner` agent.** Three `--agent council-worker --model claude-opus-4.6` dispatches: two (`q123-rh-A`, `q123-rh-C`) hit the identical FATAL and wrote NO ledger row; one (`q123-rh-E`) recorded normally. Same agent, same model, same session — so agent choice does not predict it. The differentiator was sub-agent use: rh-A and rh-C spawned sub-agents (permitted, ≤3), rh-E did not. So the guard fires when a permitted nested spawn puts a second model id in the debug log. **Consequence for receipts: any run that uses sub-agents can silently vanish from `ledger.jsonl`, so ledger-derived counts UNDER-report and "every number checkable against ledger.jsonl" quietly fails.** Reconcile dispatch counts against the on-disk OUTPUT paths, not the ledger alone. Both runs' deliverables were complete and correct on disk. Preferring `council-worker` does NOT avoid this — only avoiding opus, or avoiding sub-agents, does. **How to apply:** on this FATAL, do NOT re-dispatch blind — check the disk first (`git status --porcelain`, the declared OUTPUT path, target-file greps). Once verified, accept the work and re-dispatch only the unfinished remainder. Prefer `council-worker` for long jobs where losing the ledger row would hurt. Same acceptance posture as #2: a tool blind spot routed to judgment, never an auto-bounce.

10. **A REUSED run-id makes the wrapper refuse — and a stale ledger row then reads as success (2026-07-30, q123).** `--run-id q123-consolidate` had been used ~7h earlier. The wrapper correctly hard-refused: `copilot-worker: FATAL — output file already exists: …/q123-consolidate/result.md (run_id=…). Use a unique run-id per dispatch. Refusing to start.` No run, no new ledger row. I then grepped the ledger **by run-id**, hit the OLD run's row (`exit=0, ok=true, secs=347, deliverable=present`), and nearly reported a delivered consolidation plus a false-green stack bug. The guard worked perfectly; the misread was mine.

    Two compounding traps:
    - **`cmd 2>&1 | tail -N` discards the wrapper's exit code** — the pipeline reports `tail`'s status, so a FATAL dispatch still surfaces as "completed (exit code 0)". Redirect to a log and echo `$?` instead of piping, or the failure is invisible.
    - **Grepping the ledger by run-id alone is unsound** when ids can repeat. Match the row's `ts`/`ts_end` against *this* dispatch's window, or check the declared OUTPUT path's existence and mtime.

    Pairs with #9 as the two ways ledger-derived counts lie: #9 under-reports (a successful run writes no row), this one over-reports (a row exists from a different run). Same fix both directions — **reconcile against the on-disk OUTPUT path and its timestamp, never the ledger alone.** How to apply: make every run-id unique per dispatch (suffix `-r2`, `-hop3`, a lot name), and before believing any run landed, confirm the declared OUTPUT file exists with an mtime inside the run window.

6. **`--effort <tier>` is MODEL-SPECIFIC — an invalid tier hard-exits the wrapper (exit 2), NO run, NO ledger row.** Valid top tiers observed: `gpt-5.5` → `xhigh`; `claude-opus-4.6` → `max`; **`claude-sonnet-4.6` → `max`** (2026-07-30). `low` and `high` are NOT valid for any of the three (`--effort low` on opus, `--effort high` on gpt-5.5, and `--effort high` on sonnet-4.6 all exit 2 with `"--effort 'X' is not a valid tier for model 'Y'"`). Cost 2 dead dispatches on 2026-07-24 (graft) and **4 more on 2026-07-30** — third occurrence of the same class. Fix: **omit `--effort`** (applies the work-type cap default) OR pass the model's own top tier — `max` for both Claude tiers, `xhigh` for gpt-5.5.

    **The rejection is silent when you background the dispatch (2026-07-30 — this is what made it cost four workers instead of one).** The wrapper prints its rejection to the tee'd log and exits non-zero, but a backgrounded `… | tee log; echo "WRAPPER_EXIT=${PIPESTATUS[0]}"` surfaces to the session only as a **task-completion notification saying "exit code 0"** — the harness reports the *backgrounded shell's* status, and the `WRAPPER_EXIT` echo sits unread inside the task output file. All four dispatches read as launched; none had started.

    **How to apply:** after ANY backgrounded dispatch, `tail` the dispatch log itself before believing a worker is running. The completion notification is not evidence. A live worker writes its STEP-0 stub to the declared OUTPUT path within seconds — **the stub's existence is the real launch proof**, and its absence means the dispatch never ran. Same law as #9 and #10: reconcile against the on-disk OUTPUT path, never against a status code or a ledger row.
