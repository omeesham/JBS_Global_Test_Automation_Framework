Proven 2026-06-02 during the live QA verification campaign (40 checks, e2e + nav2).

- **`playwright-cli` (Microsoft `@playwright/cli`) is installed GLOBALLY, not in the project's `node_modules`.** Verify with `npm ls -g @playwright/cli` (→ `0.1.8`); binary on PATH at `<your-npm-global-bin>\playwright-cli`. A prior session checked `clients/encore/node_modules` only, found nothing, and wrongly pivoted to `npx playwright test` — the exact LR-054 hallucination (`playwright-cli` ≠ `npx playwright`). ALWAYS check the global install before declaring the agent-CLI unavailable.
- **One `playwright-cli state-load clients/encore/.auth/encore-state.json` authenticates BOTH e2e AND nav2.** That storageState's 26 cookies include the Microsoft SSO set (`.login.microsoftonline.com`, `.login.live.com`), which bridge nav2's (`navigator2.training.psav.com`) SSO — no separate nav2 login, no `nav2-state.json`. `playwright-cli open` defaults to **headless**, so per-worker sessions are parallel-safe (no persistent-profile lock). The persistent `e2e-profile` goes stale after ~7 days (Entra FedAuth) and shows the "Continue Now" pre-SSO gate — prefer `state-load` of the fresh storageState over the profile. nav2 shows an "Accessing Navigator…" splash for several seconds post-SSO — poll for content, don't eval immediately.
- **Subagent model gate (this environment):** spawning Sonnet or Opus subagents from an Opus-4.8-[1M] parent fails instantly with "Usage credits required for 1M context" (the child silently inherits the parent's 1M-context tier — a separate billing SKU — which the account's extra-usage doesn't cover). Only **Haiku** subagents spawn. Escalations needing Opus must run in the main loop, not as subagents.
  - **This is 1M-context-PARENT-specific, NOT a universal law** (confirmed via docs research 2026-06-04). The platform fully allows cross-class subagents (a subagent's `model` can even be *higher* than the parent's). On a **standard (non-1M) parent**, Sonnet/Opus subagents spawn freely with no gate. Fix paths when blocked: `/extra-usage` (enable the SKU) or `/model` to standard context. Sources: [Claude Code subagents docs](https://code.claude.com/docs/en/sub-agents), GitHub anthropics/claude-code #51060, #57249.
  - The `/ultra-agents` skill (`.claude/skills/ultra-agents/SKILL.md`) encodes this model-aware behavior: attempt the needed class, fall back to `inherit`/Haiku + LOG on the extra-usage error, never hard-code Haiku-only.
  - **Observed 2026-06-05 (corp-pricing planning session) — "Haiku-only" is WRONG:** from the same parent, an **Opus subagent spawned and completed successfully**, a **Sonnet subagent failed** with the 1M-credit error, and **Haiku worked**. So empirically the block hit **Sonnet**, not Opus. ALWAYS *try* the needed class first (especially **Opus** for hard/live/RCA subagent work) before any fallback; never pre-declare Haiku-only. User directive that session: "did u even try them! do not assume anything! dont use haiku for hard tasks." If Sonnet is needed, `/extra-usage` or `/model` standard-context unblocks it.

- **Copilot worker sandbox CANNOT fork Chromium (proven 2026-07-21, walk-enforce council).** A worker dispatched via `copilot-worker.sh` fails a live `playwright-cli open` with `Permission denied and could not request permission from user` — thrown at the CLI process-spawn guard **before `node.exe` starts** (Chromium is never reached; auth state is valid). Claude Code's OWN Bash runs in a different sandbox and CAN fork it. **Node-only probes still delegate fine** (e.g. the gate/denominator verification against `coverage-manifest.mjs` ran cleanly on gpt-5.5).

  - **REFINED 2026-07-30 — the block is on NAVIGATION, not on driving.** Four consecutive walk workers (pilots 4–7, Corporate Pricing → PG Override) drove the live app successfully from inside the Copilot sandbox: `eval`, `click`, `snapshot` and `network` all worked, producing real network logs, real dialog interactions and real footer readings. Only `goto`/`open` were ever refused.
  - **CORRECTED 2026-07-30 (same day, later) — session liveness is IRRELEVANT.** An earlier version of this note guessed the guard was about whether a page already existed. **Refuted by direct test:** a worker ran `playwright-cli -s=e2e goto <url>` against a confirmed-live, authenticated session and got the identical `Permission denied and could not request permission from user`. **`goto` and `open` are sandbox-blocked unconditionally for Copilot workers.** Do not write a ticket that depends on either under any circumstances.
  - **And the CEO cannot substitute.** Running the same `playwright-cli goto` from Claude's own Bash is HARD-BLOCKED by the labor gate: `LABOR GATE: Spec/test execution detected (SPEC_RUN_OR_BROWSER_WALK)`. So **nobody in the automated loop can navigate the browser to a new URL.** Once a session's page state is lost, it can only be repaired from *inside* the app (in-app routerLink clicks, dialogs) or by a human opening the page.
  - **In-app repair is not guaranteed either.** Measured on this surface: `location.reload()` does **not** re-bind the Angular office service; `location.href` jumps do not either, even from a settled routed context; and `/settings/corporate-pricing` carries **no link** to `pg-override` (1030-line snapshot, zero matches). Angular router inject failed — the root element matches neither `[ng-version]` nor `app-root`.
  - **Practical consequence: the live session is a scarce, fragile, shared resource.** Treat it as such. Confirm it before dispatching:
    `playwright-cli --raw -s=e2e eval "() => window.location.href"` — a URL back means a worker can drive it. But also confirm the page is *functional* (a known control count), because a live session sitting on a broken page will burn run after run.
  - **So the guidance is not "live walks are CEO-only".** It is: **CEO establishes the session, workers drive it.** Tell the walk ticket explicitly that `goto`/`open` are refused and that the session is already open — otherwise a worker burns its run on the gate and, worse, may substitute remembered numbers rather than reporting blocked.
