## ALL-092: Tests coupled to volatile runtime state are fragile — assert structure/behaviour, not transient data

**When**: 2026-06-26, NM-2261 Pricing Strategy deep coverage. Two PRE-EXISTING Strategy tests went red in the full-suite ×2 run (green individually / months earlier) purely from runtime-state drift, not a code change:

## ALL-093: File-upload dialogs — verify submit-trigger, write-semantics, AND failure-mode LIVE before authoring; never carry them from a plan/mental-model

**When**: 2026-07-07, NM-2305 Loc Pricing Import (first-ever import test). Three assumptions — two inherited from the plan, one from a generic mental model — were each overturned by live verification. The user's directive ("do not assume anything, check for yourself") is exactly what caught them.

1. **Submit trigger — assumed a manual "Upload" click; reality = auto-submit on file-choose.** The import dialog HAS an "Upload" button (disabled until a file is attached), so the first page-object modelled attach → wait-for-Upload-enabled → click-Upload → capture-response. **All 7 first-run TCs failed** on the Upload-enabled wait (10s timeout). The presence of a submit button is NOT proof the flow needs a manual submit.
2. **Write semantics — assumed a per-row upsert; reality = per-LOCATION replace.** The plan (and my initial artifacts) claimed "per-row upsert keyed on (LocationNo, PriceBook, Currency) — omitted rows stay intact." A 2-of-3-row file for the throwaway office DELETED its omitted 3rd row (`recordsProcessed:2`, the omitted pricebook gone from a fresh export). The import replaces a location's whole set with the file's rows for it; omitted rows are removed; locations absent from the file are untouched. **Fix**: TC-042 asserts the real replace (omitted row removed, exactly the file's rows survive) + every artifact corrected. Mutation-safety still holds because the per-test baseline file carries the office's COMPLETE row set. A silent-delete reporting lead (response says "updated 2", never mentions the delete) recorded as a discussion-item.
3. **Failure mode — assumed a 503/504 timeout; reality = HTTP 500 "Failed to replace document".** Jira tickets (NM-2009/2058/2195) describe a large-file gateway timeout; I wrote the artifacts as if that persisted, WITHOUT checking. The user challenged the assumption and authorized a one-time override to probe live: the full ~38k-row import returns **HTTP 500** with a "Failed to replace LocationPricebook document" body (NM-2407), not a 504. **Fix**: all artifacts reworded to the verified 500; TC-048 documents it as verified-once, not-automated.

**Rule going forward**: for any file-upload / import surface, live-verify BEFORE authoring the page object or TCs: (a) what actually TRIGGERS the submit (auto-fire on choose vs a manual button — capture the request with an interceptor, don't infer from the button's presence); (b) the WRITE semantics (upsert/merge vs replace — test with a file that OMITS a known row and check whether it survives); (c) the real FAILURE mode + status (don't carry a Jira-described symptom into an assertion — reproduce it).
