## § TC-LOC-LGL-019 disposition matrix — pre-implementation plan

The DOM tamper test's runtime disposition was originally framed by Phase 3.0 feasibility probe:

| Probe outcome | TC-019 disposition | Rationale |
|---|---|---|
| DOM tamper propagates to Angular form model AND server rejects | green test (assert rejection) | proves server-side validation works |
| DOM tamper propagates AND server accepts | `test.fixme()` + APP BUG filing | server lacks dropdown validation — security finding |
| DOM tamper does NOT propagate (Radix React state isolation) | `test.skip()` + NOT_AUTOMATABLE | Radix combobox stores value in React state; DOM tamper does not propagate to Angular form submission payload — observed isolation IS the correct security property |

## § TC-LOC-LGL-019 actual implementation outcome (Path D — pivot to negative-enumeration)

**Phase 3.0b live probe (2026-05-27, auth-blocked headless attempt)**: SSO redirect intercepted (auth state not pre-loaded for ad-hoc CLI session). Engineering knowledge fallback predicted Path C (Radix React state isolation).

**Phase 4 audit + spec run (2026-05-27)**: Path C hypothesis was partially wrong about the *observable*. The DOM tamper vector itself was unsafe:

- **Test run #1** (textContent + synthetic `input`/`change` events): app crashed with `Application error: a client-side exception has occurred` — page tear-down, no recovery. Synthetic events propagated to an upstream form handler that rejected the malformed event shape.
- **Test run #2** (textContent only, no events): same crash. Even text-only DOM mutation of the Radix combobox `<span>` triggers a tear-down (defensive guard, likely mutation-observer-driven).

**Live finding (Path D — discovered 2026-05-27)**: any external DOM mutation of the Radix SC combobox node crashes the Angular page. This is defensively useful (no easy text-injection vector) but blocks the originally-planned negative test via DOM tamper.

**Pivoted mechanic** (Path D-PIVOT, implemented 2026-05-27): the genuinely-uncovered mechanic per the master plan is "server-side validation of dropdown values" / "no UI path to submit invalid values". The new test implements:

- **(a) Negative listbox enumeration** — open SC listbox via `getServiceChargeOptions()`; assert `LEGAL_INVALID_SC_VALUE` is NOT among the 114 options. Proves no legitimate UI affordance exposes the sentinel value to the user (no UI path → no submission vector).
- **(b) Full save-cycle via `saveAndVerifyCase()`** — select `LEGAL_ALT_SC` legitimately, save, reload, assert persisted value is `LEGAL_ALT_SC` AND is NOT `LEGAL_INVALID_SC_VALUE`. Closes the negative end-to-end proof at the server boundary.

**Mechanic difference from TC-004**: TC-004 is positive enumeration (`toContain(default)`). TC-019 is negative enumeration (`not.toContain(sentinel)`) + full save-cycle via the FCC runner — combination NOT covered by any existing TC. STRICT-LINE-B preserved.

**Live test run (2026-05-27 11:11)**: GREEN, 21.0s. Save POST observed at 11:11:25 ("Save complete (btnSaveLegal)"); cleanup save observed at 11:11:33 (revert to "Resort Service Charge"). Two POSTs total; both legitimate values.

**Future-flip path** (network-layer extension): if a future agent runs a seeded probe with `page.route()` interception of `/navigator/api/` save POSTs to modify request body and inject `LEGAL_INVALID_SC_VALUE`, the response classification becomes:
- 4xx → server validates (defense in depth confirmed)
- 2xx → server lacks enum validation (file BUG-LOC-LGL-001, add `test.fixme()` appendix)
- This is additive to the current Path D-PIVOT assertion, not a replacement.
